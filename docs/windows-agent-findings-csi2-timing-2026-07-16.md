# Windows-agent findings — CSI2/D-PHY timing — 2026-07-16

Session goal (per `WINDOWS-AGENT-BRIEF-2-csi2-timing.md`): capture the real, working rear-camera (Samsung S5K3J1, `ACPI\INT346D`) CSI2/D-PHY receiver configuration from a genuinely streaming Windows session, to diff against Linux's `ipu6_isys_csi2_calc_timing()` computation and find the physical-layer mismatch causing CRC/sync errors on Linux.

**Bottom line: the brief's working hypothesis was based on the wrong register mechanism for this chip.** This machine's IPU6 (PCI `465D` = `IPU6EP_ADLP`, `hw_ver=IPU6_VER_6EP`) uses Intel's **MCD-PHY** implementation, which — per mainline Linux's own `ipu6_isys_mcd_phy_set_power()` — never uses the `ctermen`/`csettle`/`dtermen`/`dsettle` timing struct at all (`calc_timing()`'s output is computed generically in `ipu6-isys-csi2.c` but silently discarded for this PHY variant). Confirmed live: the `CSI2_SIP_TOP_CSI_RX_DLY_CNT_TERMEN/SETTLE_*` registers the brief named (JSL-PHY-specific) read as `0xFFFFFFFF` even with the camera actively streaming — that whole register block is simply not backed/used on this silicon. The real configuration lives in a different register block entirely, which this session did successfully read live off working hardware — see §4/§5.

## 1. RWEverything blocked by certificate revocation, not the old HVCI-based blocklist

First attempt (before any camera work) failed identically to the 2026-07-13 VCM session's RWEverything failure, but for a **different, stronger reason**: `RwDrv.sys` is now blocked by Microsoft's **Vulnerable Driver Blocklist** via outright certificate revocation, independent of HVCI/Smart App Control (both already off from the standing config):

```
Event 7000: The RwDrv service failed to start due to the following error:
A certificate was explicitly revoked by its issuer.

Event 3023 (Microsoft-Windows-CodeIntegrity/Operational):
The driver \Device\HarddiskVolume3\Windows\System32\drivers\RwDrv.sys is blocked
from loading as the driver has been revoked by Microsoft.
```

Root cause found via registry: `HKLM\SYSTEM\CurrentControlSet\Control\CI\Config\VulnerableDriverBlocklistEnable = 1` — a separate toggle from HVCI (`HypervisorEnforcedCodeIntegrity\Enabled`, already `0`) and Smart App Control (`VerifiedAndReputablePolicyState`, already `0`). Neither of those earlier toggles affects this control.

**User-authorized fix**: set `VulnerableDriverBlocklistEnable = 0`, reboot. This is a real (if scoped) security-control disable — it specifically un-blocks a driver class that's been abused for EDR-killing in real ransomware attacks (BlackByte and others) — done deliberately, with the user's explicit go-ahead, on this disposable WTG install. Confirmed **not** reverted by the subsequent reboot or by a batch of Windows Updates that installed during that reboot; `RwDrv.sys` loads cleanly now. Per user direction, this is being treated the same as the standing `testsigning`/`debug`/HVCI-off configuration from the prior session — intentional, not a leftover to revert. A future Windows Update could re-enable this flag; if RWEverything mysteriously stops working again, check this registry value first before assuming a new blocklist mechanism.

## 5. MCD-PHY handshake registers — real, live, and informative

```
PHY0 CTL    (CSI_REG_HUB_GPREG_PHY_CTL(0),    BAR0+0x238008) = 0x00000011
PHY0 STATUS (CSI_REG_HUB_GPREG_PHY_STATUS(0), BAR0+0x23800C) = 0x00000011
PHY1 CTL    (CSI_REG_HUB_GPREG_PHY_CTL(1),    BAR0+0x238010) = 0x00000000
PHY1 STATUS (CSI_REG_HUB_GPREG_PHY_STATUS(1), BAR0+0x238014) = 0x00000000
```

`0x11` = `PWR_EN`(bit0) + `RESET`(bit4) set on the CTL side, `POWER_ACK`(bit0) + `READY`(bit4) set on the STATUS side — i.e. **PHY instance 0 is powered and ready; PHY instance 1 is fully idle**, while the rear camera is actively streaming.

This is a genuinely useful, unexpected result: Linux's `ipu6_isys_driver_port_to_phy_port()` remaps logical CSI port 0 → physical PHY 1 (ports 0↔1 are swapped by that function). If that remap is correct in general, Windows appears to be driving the rear sensor through **physical PHY 0** instead, not PHY 1 — either the Linux remap logic doesn't apply the same way to this specific board/BIOS routing, or there's a further nuance (e.g. Windows numbering the port differently, or the remap only applying to certain lane-count/port combinations) not visible from the driver source alone. **This is worth flagging directly to Linux-side work**: if the Linux `ipu-bridge`/`ipu6` stack is currently assuming PHY 1 for this sensor (following the generic remap), and the real board wiring uses PHY 0, that alone could be a contributing factor to the physical-layer errors — worth checking against `media-ctl` topology or the driver's own port-assignment logs.

## 6. Full register dump — both PHY blocks (the actual ground-truth data)

`IPU6_ISYS_MCD_PHY_BASE(i) = 0x10000 + i*0x4000`, so PHY0 base = BAR0+0x10000 = `0x7FFF010000`, PHY1 base = BAR0+0x14000 = `0x7FFF014000`. Dumped `0x1960` bytes from each (covers both the `common_init_regs` region and both the "port0-style" and "port2-style" per-lane config-table regions Linux's `ipu6-isys-mcd-phy.c` defines).

**Headline finding**: PHY0 and PHY1's per-lane config tables are **near-identical** to each other (both populated with real, structured, non-garbage data — not a difference of "one has data, one doesn't"), differing only in scattered single-byte calibration/trim fields. This means both physical PHY macros get their static config tables loaded at boot regardless of which one is actively selected for a stream — the CTL/STATUS handshake in §5 is the real "which one is driving lanes right now" signal, not the table content itself.

Comparing live PHY0 data against Linux's hardcoded `x4_port0_config_regs` table (relative to phy_base) for one representative lane-group (base `0x280`):

| base+0x14 (`0x294`) | `0x23e030fa` | `0x000000fa` | low byte only |
